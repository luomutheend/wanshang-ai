# 修复说明（基于 deepseek-vela v1.0.0）

> **v1.1.0 变更（仅此一处）**：应用显示名由 `DeepSeek` 改为 `腕上AI`，同步改了启动页 logo、关于页应用名；`versionName` 1.0.0 → 1.1.0、`versionCode` 1 → 2，便于覆盖安装时被识别为升级。
> **系统包标识未动**：仍是 `org.coratech.deepseek.vela`，所以旧版本的配置、API Key、历史会话都原地继承，不会变成两个应用。
> 产物：`dist/org.coratech.deepseek.vela.release.1.1.0.rpk`（通用）与同名 JSC 版（`--enable-jsc`），签名校验均通过。

本次改动针对上一轮代码审查中列出的 P0/P1 问题，在原始工程上直接修改并重新构建、签名。此前一轮把内置接口换到阿里云百炼的 OpenAI 兼容端点，并加回**模型列表页**（`GET /models` 自动获取）；联网搜索改成完全由用户决定：开关一开就直接弹「要联网搜索吗」，不再做本地粗筛、也不再让模型先判；搜索改拿网页正文而不是摘要，资料挂在提问后面。最新一轮修的是**启动可靠性**：卡 LOGO、退出重进卡死——给所有启动期 IO 加超时、配置对象提前挂全局、启动页改成轮询加跳转重试、退出时不再阻塞写盘。

- 构建：`aiot release --enable-protobuf`（toolkit 2.0.5 / rspack 1.7.12）
- 产物：`dist/org.coratech.deepseek.vela.release.1.0.0.rpk`
- 校验：`verify-rpk-signature.js` 通过（125 个文件，hash.json 102 条摘要一致）
- 未在真机运行，交互改动建议按文末清单过一遍

### 打包产物（每次出两个包）

| 包 | 命令 | 体积 | 内容 | 适用 |
| --- | --- | --- | --- | --- |
| 通用包 | `npm run release`（`--enable-protobuf`） | 344 KB | 125 个文件，页面是 `.js` + protobuf 模板/样式 | QuickJS 引擎的机型（S1 Pro / S3 / S4 / Watch 5、6 等） |
| **Vela 5 / JSC 包** | `npm run release:s5`（`--enable-jsc`） | 358 KB | 102 个文件，9 个 `.jsc`、0 个 `.js`，纯字节码 | 只认 JSC 引擎的 Vela 5 机型（如 Watch S5） |

- 两个包共用同一份 `sign/`，包名与 versionCode 相同，不能同时装在同一个设备上。
- JSC 包内没有 JS 源码，装到非 JSC 机型会白屏/闪退，**不要混发**。
- JSC 构建后 `hash.json` 仍记录 9 个已被删除的 `.js`，所以校验要带 `--allow-missing`（工程原有 `release:s5` 脚本已处理）。
- 体积比上一版大 14 KB：多了模型列表页和 `/models` 解析，但删掉了 Anthropic 端点那条链路里不再走的部分；整体仍是 341 KB，页面脚本按需加载，不影响启动。

### 10. 渐进输出：`src/deepseek/client.js` + `src/pages/index/index.ux`

平台 `system.fetch` 只有 `success / fail / complete` 三个回调，响应结束才回调一次，拿不到 SSE 的 `data:` 分段，也没有 abort。因此改用「分段续写 + 逐字渲染」：

| 环节 | 实现 |
| --- | --- |
| 分段请求 | `chatProgressive()` 把一次回答拆成约 200 token 一段（1200 token 预算约 6 段），`finish_reason === "length"` 时把已生成内容作为 assistant 回填，再要求「从断点续写、不要重复」 |
| 边到边上屏 | 每段一到就调 `onDelta(full)`，页面立即创建/更新 assistant 气泡，并把状态条切到「正在回答…」 |
| 逐字渲染 | 页面用 45ms 一帧的定时器追帧，`step = max(1, ceil(剩余/24))`，落后越多补得越快，视觉上连贯而不是整段跳出 |
| 停止 | 「取消」把已收到的文字补显并落盘（等价于停止生成），`requestSeq` 保证迟到响应不串到下一条 |
| 深度思考 | 推理与正文共用预算、无法拆段，开启思考时仍走原来的整段请求 |
| 异常 | 中途失败时保留已生成部分并提示错误，不会让屏幕上的字突然消失 |

代价：请求数变多（1200 token 约 6 次）、续写衔接处偶有措辞重复；收益是首字从十几秒降到 1~2 秒。

### 11. 启动即新会话：`src/lib/sessions.js` + `src/pages/index/index.ux`

之前每次进入应用都会恢复上次会话，把最多 40 条消息（单条可能几百字）一次性铺进 `scroll`，手表端首屏渲染和滚动都很吃力，体感就是「卡」。

| 改动 | 说明 |
| --- | --- |
| 启动开新会话 | `onInit` 改为 `startFreshSession()`：进入应用直接落到一条空会话，首屏只渲染空状态 |
| 空会话复用 | 当前会话本来就是空的时候直接复用，不会每次启动都往历史里堆一条空记录 |
| 旧会话保留 | 原会话不出现在首页，但仍完整留在「设置 → 历史」，点一下即可切回 |
| `applySession()` 统一收口 | 切会话时一并重置 `liveIndex / pendingText / shownLen / errorText`，避免上一轮的渐进输出状态残留 |
| `onShow` 轻量判断 | 新增 `getCurrentSessionSummary()`（只读 id / updatedAt / 条数），只有确实切换过会话或消息有变才走 `getCurrentSession()` 全量规整，减少从设置页返回时的无谓开销 |

代价：启动后首页不再自动显示上一次的对话内容，需要从历史页进入；换来的是进入应用的第一屏几乎是瞬时。

### 12. 联网搜索按需触发：`src/lib/searchIntent.js` + `src/pages/index/index.ux`

开启联网后，原来每条消息都会先走一次网页搜索，连「你好」也要多等 2~4 秒。现在先在本地判断这句话值不值得搜，拿不准时照旧搜索（漏搜比多搜更影响体验）。

| 规则 | 例子 | 结果 |
| --- | --- | --- |
| 时效 / 外部事实信号优先 | 今天、最新、新闻、股价、汇率、天气、价格、发布、`20xx` 年 | 搜索 |
| 本地任务 | 翻译、润色、改写、起名、写诗、解释一下、算一下、写代码 | 不搜 |
| 纯算式 | `1+1`、`3*7等于多少` | 不搜 |
| 时间日期 | 今天几号、现在几点、星期几 | 不搜 |
| 寒暄 / 致谢 / 问能力 | 你好、在吗、谢谢、你是谁、你能做什么、hi、ok | 不搜 |
| 很短的输入（≤4 字且无问号） | 在吗、吃了吗、苹果 | 不搜 |
| 其余 | 两个模型有什么区别、推荐一款降噪耳机 | 搜索 |

状态条文案也跟着实际行为走：跳过搜索时显示「正在思考…」，不再出现「正在联网搜索…」闪一下。

### 13. 内存收敛：`src/lib/sessions.js` + `src/pages/index/index.ux`

手表上被系统杀掉重启，多数是峰值内存或 GC 抖动，不是"泄漏"。这次把几处会随使用量放大的地方收了口：

| 项 | 原来 | 现在 |
| --- | --- | --- |
| 单个会话正文预算 | 无上限（40 条，长回答每条数千字） | 30 条 + 8000 字符，超出从最旧一轮成对丢弃 |
| 会话数 | 20 | 12 |
| 保存一条消息 | `readSessions()` 把全部会话的消息重新规整一遍 | `readSessions(true)` 只带引用，仅规整当前会话 |
| 老数据 | 升级后原样保留，可能远超上限 | 首帧后 `compactSessions()` 压一次，有变化才写盘 |
| 逐字渲染 | 45ms 一帧 | 60ms 一帧，步长同步放宽，临时字符串少三成 |
| 补滚定时器 | 每次 `scrollToBottom` 加 2 个 timeout，不清理 | 只保留最新一批，`onDestroy` 统一清 |
| 页面销毁 | 只停两个定时器 | 额外清补滚定时器，并主动置空 `messages / history / pendingText / inputText` |

没有改动的部分：日志本身有 200 条内存上限 + 5s 批量落盘；键盘词库有 `release()/destroy()`；`vmPool` 每 10s 清理失效页面实例。这三处原本就是收敛的。

剩余的最大内存项是键盘首次弹出后常驻的图片与节点（`keyboardCreated` 保活，避免每次弹键盘都重建 1 秒），属于"速度换内存"的取舍，本次未动。

### 14. 启动路径去掉同步 IO：`src/app.ux` + `src/lib/sessions.js` + `src/pages/index/index.ux` + `src/lib/store.js`

「切几次页面再进来卡在启动页」不是内存问题，是**启动路径上串了太多同步活**。首页 `onInit` 里原来依次做 `compactSessions()` → `getCurrentSession()` → `createSession()`，每一层都会把十几条会话的全部消息重建一遍，`createSession()` 还会立刻把整包会话落盘。会话越多、切页次数越多，这一次越慢，而启动页要等新页面首帧渲染完才消失，表现就是一直停在 logo。

| 项 | 原来 | 现在 |
| --- | --- | --- |
| 首页启动 | 读全部会话 3 次、写盘 1~2 次 | **零读零写**：只生成一条内存草稿会话 |
| 草稿会话 | 启动即 `createSession()` 落库，即使一个字没发 | 不落盘、不进历史；发出第一条消息时由 `saveMessages(..., isDraft)` 补插，创建与保存合并成 1 次写入 |
| `compactSessions()` 判定 | 用数组下标对比 `raw[i]` 与排过序的 `list[i]`，两者顺序不同 → 永远判成「有变化」→ 每次启动都重写整包会话 | 改为按会话 id 对照，并补上「条数超限」判断；实测连续两次调用增量均为 0 |
| `compactSessions()` 时机 | `onInit` 里同步执行，直接挡在首帧前 | 延后 3 秒，页面可交互后再压 |
| 启动诊断 | `runStorageDiagnostics()` 在 `onCreate` 里 `await`，要跑 4 轮存储/文件读写才 `resolveReady()` | 先 `resolveReady()` 放行启动页，诊断转到后台，只写日志 |
| 旧文件读取 | 每次启动都并行 parse 一份 `deepseek-store.json` | 只有 storage 与当前文件都为空时才读（纯迁移用） |
| 历史页列表 | `readSessions()` 全量裁剪 12 条会话的每条消息 | `readSessions(true)`，只取标题与时间 |
| 切会话 | `openSession()` 全量重建后挑一条 | 只重建被点开的那一条 |
| `onShow` 重铺 | — | 当前是未落盘的空草稿时直接返回，避免被「上一条会话」顶掉；`openSession()` 会写 `global.__sessionSwitchedAt`，用户刚在历史页切过会话时照常加载 |

> 代价：空会话不再立刻出现在历史里，要等发出第一条消息。这是刻意的——历史页本来就过滤空会话，落不落盘对用户没有区别，但省掉了每次进应用的两次整包序列化。

### 15. 收敛 storage / file 调用：`src/lib/store.js` + `src/lib/apiKeyStore.js` + `src/lib/log.js` + `src/lib/diag.js`

Vela 上 `@system.file` 调用次数一多就容易把应用拖进重启。这次按"能不打就不打"重排了所有持久化路径：

| 场景 | 原来 | 现在 |
| --- | --- | --- |
| 冷启动读配置 | storage + 当前文件 + 旧文件 + 两个镜像，5 路并行（旧文件每次启动都 parse） | 只读 storage 一次；读不到才依次看文件备份、旧文件、镜像 |
| 保存配置/会话 | 每次都 storage + file 双写 | storage 成功即结束，file 只在 storage 失败时兜底 |
| 加载 API Key | `ensureDir` + storage + 2 个文件读 + 可能回写，4~5 次 | storage 命中即返回（1 次）；未命中才读文件 |
| 保存 API Key | storage 写 + 读回校验 + 文件写 + 读回校验 + 删旧文件 | storage 写一次；失败才落文件。不再读回校验 |
| 启动诊断 | 每次冷启动 6 次读写 | **启动不跑**，改为「关于」页连点版本号打开诊断时执行一次 |
| 日志初始化 | 构造函数里 mkdir + list + delete | 第一次真正落盘时才建目录、清旧日志；启动阶段 0 次 |
| 日志落盘间隔 | 5s | 15s（仍是批量追加） |

正常使用下，一次冷启动的文件接口调用从 10 次以上降到接近 0；只有真正发生配置/会话变更时才会写一次 storage，且不再同时写文件。

### 16. 返回动画修复 + 开关：`src/lib/ui.js` + 各页面 `onInit` + `src/pages/settings/settings.ux`

动画"消失"是两个原因叠出来的：

1. `vmPool` 里根本没有当前页实例。只有带 `PageHeader` 的页面在组件 `onInit` 里注册过，而且用的是 `router.getState().name`——`onInit` 阶段这个值在部分固件上还是上一页，会把 VM 注册到错误的 key 下；首页干脆没有注册。
2. `runGC` 用 `vm.$valid` 判断存活，但 Vela 的页面对象没有这个属性，于是**每 10 秒就把整个 vmPool 清空一次**。所以进页面头几秒有动画，过一会儿就没了。

| 项 | 现在 |
| --- | --- |
| 注册 | 首页、设置、API Key、历史、关于、余额、统计，各自在 `onInit` 里 `InitPage(this, "pages/xxx")`，用显式路径 |
| `PageHeader` | 删掉组件里的推断式注册，避免把 VM 挂到错误的 key 下 |
| `runGC` | 改为比对 `router.getPages()` 里还在的页面名，只清已经出栈的；拿不到栈信息时这一轮不清理 |
| 入场动画残留 | 上一页的 `scroll-frombackanim` 在动画播完后落到 `scroll-anim-done`（`animation-name: none`），不再清空成 `""`——清空会让 `.scroll` 自带的 `openpage-scroll` 重新播放，看起来就是「返回动画播了两遍」 |
| 切会话自动退两步 | 设置页自动 `router.back()` 直接退，不再走一轮动画，少等约 0.5 秒 |
| 动画开关 | 设置页新增「返回动画」开关（默认开），存于 `deepseekBackAnim`；关闭后 `onBackPress` 直接返回，不做任何动画与延时 |

> **动画重复播放的根因**（本轮修）：页面的滚动容器固定带 `class="scroll"`，而 `.scroll` 里写死了 `openpage-scroll` 入场动画。返回流程结束时如果把这个 class 清成 `""`，class 一变，浏览器/CSS 引擎就会把 `openpage-scroll` 当成「新动画」重新跑一遍：上一页刚滑入就被瞬移回起点再滑入一次，视觉上就是动画播了两次。修法是给动画结束态一个显式的 `scroll-anim-done { animation-name: none; }`，离开页则用 `scroll-backanim-finished`（同样带 `animation-name: none`）。**任何地方都不要再用 `scrclass = ""` 收尾。**

### 18. 联网搜索：彻底交给用户，并修掉「搜了却说不知道」

上一版做的是「本地粗筛 → 模型判断 → 用户确认 → 搜索」。实测发现开了联网仍然经常答「不知道」，问题出在中间那两层判断上，现已全部删除。

**为什么会出现「搜了等于没搜」**

| 环节 | 问题 |
| --- | --- |
| 模型判定 | 判定请求本身带了原问题（`{role:"user", content: q}`），字段没问题；但模型会把问题压缩成更窄的检索词，例如「小米 Watch S5 什么时候发布的」被压成「小米 S5 发布」，检回来的东西和原意对不上 |
| 读的是摘要不是正文 | 原来 `need_content: false`，拿到的是服务端二次概括的 `summary`。概括会把数字、限定条件、时间状语抹掉，模型据此回答自然「不知道」或答偏 |
| 资料位置 | `<search_results>` 拼在 system 里，排在几十条历史之后，注意力被冲淡，模型手里拿着资料也照样回「不知道」 |
| 超时 | 搜索超时 30 秒，手表走蓝牙/弱网时很容易踩线，超时后按「没搜到」处理，静默退回无资料回答 |

**现在的流程**

联网开关打开 → 提问 → 直接弹确认条（检索词就是原问题，一个字不改）→ 点「联网」才搜，点「不用」就按离线答。没有本地粗筛，没有模型判定，也不改写检索词。

| 文件 | 改动 |
| --- | --- |
| `src/pages/index/index.ux` | 删除 `shouldSearch` / `judgeSearchNeed` 调用；`searchOn` 为真时直接 `askSearchConfirm(question)`；`searchWeb(question, question, 6)` 的 query 与 ori_question 都用原话 |
| `src/pages/index/index.ux` | `buildMessages` 把 `<search_results>` 挂到最后一条用户提问后面，并在 system 里明确「资料里写明了就直接回答，不要再说不知道」 |
| `src/deepseek/client.js` | `need_content: true`，直接拿网页正文；`buildSearchContext` 正文优先（每条约 1200 字），正文抓不到时才退回 summary / snippet（500 字），总量上限 10000 字 |
| `src/pages/index/index.ux` | 搜索条数传 8 作为**上限**，不是配额：服务端按相关性返回，搜不到那么多就给更少，代码不补足；并在提示词里说明「不必逐条引用，用得上几条就用几条」 |
| `src/deepseek/client.js` | 搜索超时 50s、不重试（原 30s×2 次，最长要等 90 秒）；`count` 用 `Math.min(n, 8)` 兜住上限；新增日志「N 条结果，正文 X 条，摘要兜底 Y 条」「接口返回空结果」 |
| `src/deepseek/client.js` | `judgeSearchNeed` 保留但标注未启用，回退时可用 |

确认条细节：盖在状态条位置，显示标题「要联网搜索吗？」、检索词原文、小字「15 秒不选按「联网」走」，两个按钮「不用 / 联网」。等用户决定期间停止计时，15 秒无操作按「联网」继续（开关本来就是开着的）；点状态条「取消」则视为不搜并中止本次提问。

设置页「搜索前确认」开关保留，默认开。关掉它则联网一开就自动搜，回到最简行为。

关于「模型判定是不是没带上问题」：判定请求里确实带了，`messages` 是 `[system, {role:"user", content: 原问题}]`，没有丢。真正的问题在判定结果的 `query` 会覆盖原问题，以及上面列的摘要截断和资料位置。这两层现在都不再参与。

### 19. 启动卡 LOGO / 退出重进卡死：`src/app.ux`、`src/pages/splash/splash.ux`、`src/lib/store.js`、`src/lib/apiKeyStore.js`、`src/lib/ui.js`、`src/pages/index/index.ux`、`src/pages/settings/settings.ux`

现象：启动时停在 LOGO 不动，退出后重新进入有概率直接卡死。这是几个问题叠在一起，任何一个踩中都会卡住，所以表现为「有概率」。

**根因**

| 环节 | 问题 |
| --- | --- |
| `app.ux` | `global.config = Config` 写在 `await Config.init()` **之后**。storage 一旦不回调，`onCreate` 永远停在这一行，`global.config` 是 `undefined`，页面 `onInit` 里 `global.config.read(...)` 直接抛异常 |
| 全部启动期 IO | `storage.get` / `file.readText` / `file.mkdir` / `file.writeText` 都是纯 `await`，Vela 在启动瞬间或销毁阶段偶发不回调，Promise 永久挂起，没有任何超时兜底 |
| `splash.ux` | 只在 `global.ready` 有 `then` 时等待，否则**立即跳转**。跳转时配置可能还没就绪，首页一进去就崩在 `onInit`；`router.replace` 抛异常也没有重试，一抛就停在 LOGO |
| `splash.ux` | 2 秒兜底 `setTimeout` 与 `global.ready.then` 两条路径都会跳，`router.replace` 被调用两次的概率不为零 |
| `app.ux` `onDestroy` | `await store.flush()` 没有限时。退出时 storage 不回调就挂住，应用停在「正在退出」的半死状态，再次进入更容易卡 |
| `app.ux` `onDestroy` | 退出时还调 `logger.flush()`，触发 mkdir + list + writeText 三次文件调用——正是 Vela 上最容易出问题的时段 |
| `ui.js` | 10 秒一次的 `runGC` 在后台继续跑，退出过程中仍在调 `router.getPages()` |

**改法**

1. **配置对象提前挂全局**：`onCreate` 第一行就 `global.config = Config`，再做异步初始化。`store` 构造函数里已经装好 `DEFAULT_CONFIG`，所以即使 init 没回来，页面读到的也是可用默认值，不会 `undefined`。
2. **所有启动期 IO 限时**：`Config.init` 2.5 秒、`getDeviceInformation` 1 秒；`store` 的读 1.5/1.2 秒、写 1.5 秒；`apiKeyStore` 读 1.2/1.0 秒、写 1.5 秒；mkdir 1.2 秒。超时按失败处理，继续往下走，绝不无限等待。
3. **放行一定有保证**：`resolveReady()` 挪到 `onCreate` 末尾，且每个 `await` 都包在 try/catch 里——不管初始化成功、失败还是超时，启动页都会被放行。
4. **splash 改成轮询 + 重试**：每 150ms 检查一次 `global.bootDone`（启动各阶段全部跑完后才置位），最多 30 次（约 4.5 秒），到点无论如何都跳。`router.replace` 失败重试 2 次（间隔 250ms），最后再试一次 `router.push`。`jumped` 标志保证只跳一次，避免两条路径重复跳。
5. **退出不阻塞**：`store.beginExit()` 后落盘只尝试一次 storage，不再走 `mkdir + writeText` 兜底；`withTimeout(store.flush(), 600)`，600ms 写不完就放弃。退出不再刷日志文件（15 秒批量落盘，最多丢最后十几行）。
6. **前后台切换停定时器**：`ui.Pause()` / `ui.Resume()`，`app.ux` 的 `onHide` / `onShow` 分别调用。`Resume` 不会重置 `vmPool`，返回动画不受影响。
7. **页面读配置兜底**：`index.ux` / `settings.ux` 新增 `configOf()`——`global.config` 不可用时退回 `global.__dsStore`（同样有默认值），再不行返回一个空配置对象。所有 `global.config.read/write` 调用点改走它，页面 `onInit` 不会再因为配置缺失抛异常。
8. **首启减少文件调用**：`initApiKey` 的迁移路径从「串行读 3 个文件 + 1 次 storage」收敛为「1 个文件 + 1 次 storage」，首启总接口调用从最多 6 次降到 4 次。代价是更老版本（按服务商分存那一版之前）的 Key 不再自动迁移，需要重填一次。

**为什么是「概率性」**：`storage` 不回调、`router.replace` 抛异常、`onCreate` 与 `splash.onInit` 的先后顺序，这三者都依赖固件调度，每次启动都可能不一样。改动后每条路径都有确定的终点：最坏情况 2.4 秒进首页，配置读到的全是默认值。

**已知取舍**：如果 `Config.init` 真的超时了，用户这次启动会看到默认配置（内置接口、联网开、200 字上限），已保存的模型选择和开关要等下次启动才生效。这比卡在 LOGO 上强。

### 20. 启动改成「一起加载 + 放慢节奏 + 把内存回收做掉」

上一版为了避开启动内存峰值，把会话改成了「用到才加载」。这不是想要的效果：配置和历史本来就该在启动时一起就绪，问题出在**同一瞬间把解析、拷贝、序列化全挤在一个事件循环里，用完的中间对象又没人放**。这一版按「照常加载、放慢节奏、逐段回收」重做。

**加载：一起加载，但不挤在一起**

| 阶段 | 内容 | 超时 | 之后 |
| --- | --- | --- | --- |
| 1 config | `store.init()`（配置 + kv + 旧会话摘出） | 2.5s | 让出 24ms |
| 2 key | `initApiKey()` | 1.2s | 让出 24ms |
| 3 sessions | `warmup()`（历史会话） | 2.5s | 让出 24ms |
| 4 device | 设备信息 + 设备档案 | 2.5s | 让出 24ms |

`splash` 不再看「`global.config.read` 存不存在」（那个在 `onCreate` 第一行就有了），改成等 `global.bootDone`——四段全跑完才置位，所以进首页时配置和历史都已经就绪。轮询上限放宽到 30 次（4.5 秒），只作为「某一段真的卡死」的兜底。

会话加载本身也分批：先建索引（标题/时间），再规整正文，每 3 条 `await sleep(1)` 让出一次。几十条会话的实际加载耗时仍在 10ms 量级，但峰值被摊开了。

**回收：四层**

1. **单份驻留**：会话从 `store.json` 的 kv 里摘出来，迁到独立键 `deepseek_sessions_v1`（文件兜底 `dsdata/sessions.json`）。启动时从 kv 读出后立刻 `store.remove("chatSessions")`——以前这份数据在 kv 和页面各存一份，每次 `store.flush()` 还要把它整个 `JSON.stringify` 一遍。
2. **解析完就断引用**：`JSON.parse` 出来的原始数组用完立刻 `raw = null`、`legacy.length = 0`；`store.flush()` 里拼出来的那串文本写完 `text = null`。QuickJS 是引用计数 + 标记清除，早断引用就早回收，不用等下一轮。
3. **写盘合并**：会话写盘从「每发一条消息写一次」改成 1.8 秒窗口合并，一串对话只写一次；退出 `onDestroy` 补一刀（限时 500ms），切后台 `onHide` 也补一次（不 await）。写失败保留 `dirty`，下轮再试。
4. **空闲回落**：空闲 12 秒后，非当前会话的正文只留最后 4 条（2 轮），完整内容留在磁盘，列表页仍显示原始条数。用户点开时按需读回——只有那一条，读完即释放。

**冷回落的坑（已堵）**：回落后再发消息会触发写盘，如果直接序列化内存里的 4 条，磁盘上的完整历史就被截断了。所以写盘前先把冷会话的正文从磁盘临时补回来（`hydrateColdForWrite`），写完立刻再裁回 4 条。这一步只在「有冷会话 + 确实要写盘」时发生，不在启动路径上。

**顺手修掉的一个真问题**：`lib/ui.js` 只导出了小写的 `init` / `initPage` / `onBackPress`，而 `app.ux` 和所有页面调的是 `ui.Init` / `global.ui.InitPage` / `global.ui.OnBackPressTriggered`——全是 `undefined`。也就是说页面实例**从来没注册进 `vmPool`**，10 秒一次的 `runGC` 和返回动画的实例查找一直没生效。现在补了兼容导出，并在页面实例出栈时主动清空它的 `messages` / `history` / `sessions` 数组。

**防覆盖**：会话没成功加载过（`loaded === false`）时一律不写盘。否则空 cache 一落盘，磁盘上的历史就整包没了。

**验证**：用模拟的 `storage` / `file` / `store` 跑了 6 组用例，全部通过——

| 用例 | 结果 |
| --- | --- |
| 14 条旧会话迁移：收敛到 12 条、单条正文 ≤ 8000 字、消息 ≤ 30 条、按更新时间排序 | 通过 |
| kv 旧副本删除 + 迁移后立刻写独立键 | 通过（43.9 KB） |
| 发消息后 1.8 秒内不写盘，`flushNow` 立刻补写 | 通过 |
| 冷回落：11 条非当前会话裁到 4 条，列表页条数不变 | 通过 |
| 冷回落后写盘：磁盘仍是完整正文，内存仍只有 4 条 | 通过 |
| 点开冷会话：完整正文读回（30 条） | 通过 |
| `store` 未就绪时 `warmup` 返回 null 且禁止写盘 | 通过 |

**真机请重点看**：冷启动到首页的时间（应在 1 秒内）、连发 5 条消息后退出重进历史是否完整、历史页点开一条较早的会话能否看到全部内容、往返「首页 → 历史 → 首页」10 次后内存是否稳定。

### 21. 检索词交给 AI 结合上下文判断，搜索固定取 10 条

官方 Search 接口（`POST /v1/tools/search`）的完整参数：`query`（1~128 Unicode 字符，不能全空白）、`count`（1~50，**默认 10**）、`ori_question`（1~128 字符，帮助理解意图，`null` 视为未提供）、`localization`（默认 `""`）、`need_content`（默认 `false`）。之前我们把 `count` 写死成 8，检索词也只参考最近 2 轮对话，追问时容易搜偏。

**先说一个文档事实**：接口没有「条数留空由 AI 决定」的机制——不传 `count` 就是固定 10 条，传 0 会直接 400（`'count' must be between 1 and 50`）。所以「让 AI 自己选条数」只能靠我们自己让模型输出，或者干脆固定。这一版选择**固定 10 条**：条数稳定，资料覆盖面才稳定，不会同一类问题这次看 10 条、下次只看到 6 条。

**改法**

| 项 | 之前 | 现在 |
| --- | --- | --- |
| 上下文窗口 | 最近 4 条消息，每条 300 字 | 最近 8 条消息（4 轮），每条 400 字 |
| 提炼提示词 | 只要求「把指代从上文找出来」 | 先判断这次问的是什么：追问就把上文的对象/型号/地点/时间补进检索词；新话题只按这次的问题写，不混入上文 |
| 时间限定 | 无 | 只有问题明确指向近期信息时才让模型加 `after:年份`，没有明确指向就不加 |
| 搜索条数 | 写死 `count: 8` | 固定 `count: 10`（接口默认值，显式写出；按请求次数计费，条数不影响价格） |
| 原始问题 | 已传 `ori_question` | 保留，截断 128 字符（接口上限） |
| 结果过滤 | <1.0 分全丢，全低分只退前 3 | <0.8 分丢弃，且**保底 6 条**——过滤太狠会让回答只剩一两条依据，结论片面 |
| 正文预算 | 每条 1200 字、总量 10000 | 每条 900 字、总量 11000——10 条都能进上下文，不让前三条吃掉全部预算 |

**验证**：抽取 `client.js` 里的真实函数，mock 请求层跑了 5 组用例，全部通过——

| 用例 | 结果 |
| --- | --- |
| 12 条历史 → 只取最近 8 条，每条 ≤ 400 字，首条 system、末条当前问题 | 通过 |
| 请求体 `count` 恒为 10，`need_content: true`，带 `ori_question` | 通过 |
| 只有 2 条高分时仍保底 6 条；10 条全优时全留；结果不足 6 条时不虚构 | 通过 |
| 10 条 × 1600 字正文 → 10 条全部进上下文，总长 9356 字，第 10 条没被裁掉 | 通过 |
| `query` 与 `ori_question` 均截断到 128 字符 | 通过 |

### 22. 结果分数太低时重新提炼检索词再搜一次

上一版遇到「搜回来的全是无关页」只能硬着头皮把低分结果塞给模型，或者干脆说不知道。现在加一层兜底：第一次结果质量不达标时，**带着上下文重新提炼一个检索词再搜一次，最多一次**。

**什么算「低分」**

| 条件 | 说明 |
| --- | --- |
| 一条都没搜到 | 直接重搜 |
| 最高 `rerank_score` < 1.2 | 全批都接近无关页 |
| 优质条数（≥1.5）< 2 条 | 只有一两条能用的，回答容易片面 |

**重搜用什么词**：让模型看着对话上下文重新提炼，不是把原话丢回去。

第一次的词是「窄而准」，如果连它都搜不到高分结果，说明这个方向本身就不对。原话虽然宽，但和第一次的词往往只差几个虚词，撞回同一批站点的概率很高，等于白搜一次。重提炼时把上一轮的词写进提示词，明确要求换角度：同义词、上位词、更具体的型号、英文原名、去掉过窄的限定，不要只调换词序或加个年份。

只有模型也给不出另一个词（空结果、或与第一次同词）时才退回原话；原话也和第一次同词就不搜了——同一个 query 重发只会拿回同一批结果。

**合并而非替换**：两批结果按 URL 去重后一起重排，第一次里的高分条目不会因为重搜被丢掉；排序后仍按原规则保留（≥0.8 分、保底 6 条），并新增**上限 10 条**——两批最多 20 条，全塞进上下文会把 11000 字的预算吃光，后面的条目连正文都进不来。

**失败与超时**：重提炼 10 秒、重搜 35 秒（首次搜索是 50 秒）；任一步失败或没结果就沿用第一次的结果。状态条分两段显示：「结果不理想，重新提炼检索词…」→「换个说法搜「新词」…」，不让用户以为卡住了。

**验证**：mock 请求层跑了 11 组用例，全部通过——

| 用例 | 结果 |
| --- | --- |
| 第一次 0 条 → 重新提炼后搜第二次；第二次 `query` 是新词，仍带 `count: 10` / `ori_question` / 35s 超时 | 通过 |
| 重提炼请求的 system 含「上一轮的检索词是「…」」「换一个角度」，末条是用户原话 | 通过 |
| 第一次 10 条全 0.5 分 → 重搜；合并 20 条后按分数取前 10 | 通过 |
| 第一次 10 条全 2.0 分 → 不提炼、不重搜 | 通过 |
| 模型给回同一个词 → 退回原话搜 | 通过 |
| 提炼抛错 → 退回原话搜 | 通过 |
| 提炼为空且原话与首次同词 → 不重搜，沿用第一次 | 通过 |
| 重搜抛错 → 沿用第一次，不崩 | 通过 |
| 同一 URL 在两批都出现 → 去重为 1 条 | 通过 |
| 重搜后仍低分 → 不再请求第三次 | 通过 |
| 阶段回调顺序 refine → search(新词)；回调抛错不影响搜索 | 通过 |

### 23. 退出后立刻重进导致数据全丢（只剩 API Key）

**现象**：退出应用后马上重进，模型选择、开关、历史会话、统计全部变回初始状态；杀掉应用或重启设备后再进，数据又回来了。

**根因**：不是数据被删，而是启动时**没读到**，随后又把内存里的默认值写了回去。

| 环节 | 原来的行为 |
| --- | --- |
| `store.init` | `storage.get` 在退出后重进的头一两秒经常不回调，1.5 秒超时被当成「没有数据」→ 用默认配置 + 空 kv，并 `_schedule()` 在 300ms 后落盘 |
| `sessions.warmup` | 同样把读超时当成「没有历史」→ `loaded = true`、`cache = []`，用户一发消息就把空列表（加一条新会话）写回磁盘 |
| API Key | 独立存在 `apiKeyStore`，读写路径不经过上面两处，所以只有它活了下来 |

重启后能恢复，是因为那次写入多数也失败了（storage 整体不可用），磁盘上的原数据没被覆盖。但只要有一次写成功，就是真的丢。

**修复**

1. **读取改成三态**：`{ok:true, data}` / `{ok:true, data:null}`（读成功、确实是空）/ `{ok:false}`（超时、异常、内容损坏）。只有「读成功且确实为空」才允许写默认值。
2. **只读模式**：`loadFailed` 期间 `_flushOnce` 直接返回，保留 `dirty`，一次都不写；`sessions` 读失败时不再置 `loaded`，`flushNow` 的 `loaded` 检查天然挡住所有写盘。
3. **启动内重试**：`store.init` 第一次读失败后隔 250ms 再读一次，同时把文件兜底那几路提前发出去（并行，不串行等两轮超时）。
4. **首屏后补读**：`app.ux` 在 `bootDone` 之后轮询等待 `store.ready`，再调 `store.retryLoad()` 与 `sessions.warmup()`；读不到就什么都不做，绝不覆盖。
5. **补读合并顺序**：默认值 → 磁盘 → 本次启动用户改过的字段。用户在只读期间改了开关，补读回来也不会被旧配置盖掉（`write()` 会记下改了哪几个键）。
6. **首页晚到接管**：历史补读成功时，只有当前还是空草稿、没输入任何字、也没在生成回答，才把空对话换成真正的会话，等 6 秒还没到就保持空对话。
7. **写盘异常不再上抛**：`Config.write/save` 吞掉 flush 异常，设置页不会因为一次写失败弹错误。

**验证**：用回调式 mock（模拟 Vela 的 `storage.get/set` 永不回调）跑了 9 组，全部通过——

| 用例 | 结果 |
| --- | --- |
| storage 不回调 + 文件读不到 → 标记 `loadFailed`，`flush` 一次都没写 | 通过 |
| 只读期间改配置 → `flush` 仍然不写 | 通过 |
| 补读成功 → 磁盘上的模型/统计接回来，用户刚改的开关不被覆盖 | 通过 |
| 首次安装（读成功且为空）→ 正常写默认值 | 通过 |
| 内容损坏 → 不当空，不覆盖（留着还有人工救的可能） | 通过 |
| 写盘超时 → 返回 false，保留 dirty 等下次 | 通过 |
| 会话 storage 不回调 → `warmup` 返回 null、`isLoaded` 保持 false、不写盘 | 通过 |
| 会话补读成功 → 旧会话回来，再保存时新旧都在，旧的不被覆盖 | 通过 |
| 会话内容损坏 → 不当作空历史，不覆盖 | 通过 |

### 24. 检索词提炼改为带整个会话，不截条数也不截字数

上一版只把最近 8 条（4 轮）、每条 400 字交给提炼模型。对话一长就出问题：话题跨过截断点之后，前面定过的型号、地点、预算全丢了，追问「那它多少钱」会被压成「它 多少钱」，搜回来的东西自然对不上。

**改法**

| 项 | 之前 | 现在 |
| --- | --- | --- |
| 历史条数 | 最近 8 条 | **整个会话，一条不丢** |
| 单条长度 | 400 字 | **不截断**，助手回复里的型号、价格、结论都在后半段 |
| 当前提问 | 截 300 字 | 不截断 |
| 提炼超时 | 10 秒 | 15 秒（输入变大，仍不能拖住搜索） |

**唯一删的东西是网页正文**：历史轮次的用户消息里会挂着上一轮的 `<search_results>…</search_results>`，那是资料不是对话，几万字塞进提炼请求只会让模型找不着重点。这里只剥掉这个资料块，对话本身一字不删（`stripSearchContext`）。

上下文由服务端处理，不占手表内存；手表只是把这段 JSON 发出去。

**验证**（抽取真实函数 + mock 请求层，6 组）

| 用例 | 结果 |
| --- | --- |
| 30 条历史（15 轮）→ 请求里 32 条消息，第 0 轮仍在 | 通过 |
| 813 字的助手回复完整进入请求，结尾的结论没被切 | 通过 |
| 历史含 1.2 万字 `<search_results>` → 资料块剥净、原话保留 | 通过 |
| 重提炼（低分重搜）同样带全部 30 条 + 上一轮词 | 通过 |
| 剥离函数：普通文本不变、空值安全、整条都是资料时返回空 | 通过 |
| 空历史 → 只发 system + 当前提问 | 通过 |

**注意**：这一节只改检索词提炼，回答侧的上下文窗口见下一节。

### 25. 回答也带整段会话；长对话默认只渲染最近 20 条

检索词已经全量了，但回答模型当时只收到最近 12 条（约 6 轮）。聊到十几轮之后，前面定过的型号、预算、结论全在窗口外，模型就开始「乱讲话」——它不是忘了，是根本没收到。

**改了三处窗口**

| 位置 | 之前 | 现在 | 作用 |
| --- | --- | --- | --- |
| `buildMessages`（发给模型） | 最近 12 条 | **整段会话** | 回答不再丢前文 |
| `HISTORY_LIMIT`（页面内存） | 30 条 | **120 条**（约 60 轮） | 会话本身够长 |
| `lib/sessions.js` 持久化 | 30 条 / 8000 字 | **120 条 / 24000 字** | 退出重进后前文还在 |

**渲染改成窗口 + 上滑加载**

- 首屏只铺最近 **20 条**（约 10 轮），更早的不进 `messages`，不参与渲染。
- 列表顶部显示「上滑加载更早的 20 条」，滑到顶（`scrollTop ≤ 24`，含回弹负值）自动补一批；点这一行也能加载，防止个别固件上滚动事件不灵。
- 每批 20 条，300ms 冷却，避免贴顶时连续触发把几十条一口气全加载。
- `history` 始终是完整会话：发给模型、写盘、算 token 都用它；`messages` 只是渲染窗口。渐进输出那条气泡的下标会按窗口起点换算（`liveIndex - renderStart`），不会画错位置。
- 发新消息时窗口自动收回到最近 20 条——反正视图会滚回底部；往上翻到很早的位置再发消息，也不会因为窗口无限变长而卡。

**验证**：`node --check` + 抽取脚本做语法校验通过；渲染窗口的起点换算、顶部提示条的显隐、`paintLive` 偏移在代码里逐处核对（共 6 处 `this.messages` 赋值，全部改成带 `renderStart` 的切片）。

## 二、兼容与迁移

1. **API Key**：老用户升级后，`store.json` 里的 Key 在首次启动时被读入内存并复制到 `apiKeyStore`；之后 `store.json` 不再含 Key。根目录 `deepseek-api-key.txt` 会被自动删除。
2. **Key 结构**：回到单 Key（`deepseek_api_key_v1`）。上一版写下的分服务商 JSON（`deepseek_api_keys_v2` / `api_keys.json`）会在首次启动时读取其中 `deepseek` 那份，并回写成单 Key，用户不需要重填。
3. **配置**：`store.json` 结构不变，仅少了 `deepseekApiKey`。上一版残留的 `apiProvider` / `apiBaseUrl` / `apiModel` / `apiKeys` 字段不再读取，也不影响启动；`apiMode` 缺失时按 `builtin` 处理。
4. **模型**：回到 `deepseekModel`。上一版迁移写入的 `apiModel` 不再使用——如果用户在上一版里换过 DeepSeek 模型，会回落到 `deepseek-flash`，重新点两下即可。
5. **会话**：从 `store.json` 的 `kv.chatSessions` 迁到独立键 `deepseek_sessions_v1`（文件兜底 `dsdata/sessions.json`）。首次启动自动迁移，迁移完立刻写独立键、再从 kv 删除旧副本；更老的单对话 `chatHistory` 会迁成一条历史会话。统计仍留在 `kv.tokenStats`，未改动。
6. **存储格式 v2**：整包 JSON 增加 `v2: 1` 字段。老数据没有这个字段，所以这一版**第一次**启动仍会读一次 `dsdata/store.json` 做时间戳比对；取较新的一份并补写标记，之后启动不再读文件。
7. **新增配置项**：`apiMode`（默认 `builtin`）、`builtinModel`（默认 `deepseek-v4.1-flash`）、`deepseekBackAnim`（默认开启）。老用户存的 `qwen-plus` 在新端点下依然可用，不会失效。老配置里没有的字段按默认值处理，回滚到旧版本也不影响。
8. **签名**：使用工程自带 `sign/private.pem` 重新签名，包名、versionCode 不变；覆盖安装需保证设备上原包为同一证书签名。

## 五、仍未处理

1. **逐 token 的 SSE**：平台 fetch 无增量回调，当前为「分段续写 + 逐字渲染」。要做真 SSE，需要自建中继：把上游的 SSE 存成累积快照，手表轮询 `/snapshot?id=`；每条回答会增加数次短请求，且需要一台服务器。
2. **Key 加密存储**：Vela 未提供 keystore，只能做到减少副本 + 掩码显示；如设备支持安全存储可再接入。
3. **内置 Key 是明文的**：写死在包内，任何人解包都能看到；额度用尽、被限流或服务方停用后就不可用，且没有备用通道。这是「免配置」的代价，只适合个人自用，不要公开分发。真要长期稳定，需要自己的中转服务与额度控制。
4. **模型列表没有搜索/分组**：125 个模型靠滚动找，手表上翻起来比较累。常用模型已排在最前，真要快速定位还得靠下一版加筛选或分组。
5. **单条会话删除**：`deleteSession()` 已实现但历史页没有入口，本次未加长按菜单。
6. **`withTimeout` 不中断底层请求**：平台无 abort 接口，仅在 UI 层丢弃结果。
